# Epic planning tier

**Decision.** Work larger than one squash-merge (`#git-branch-workflow`) is planned in an **epic** (`#swe-epic`): a mutable, topic-scoped directory under `docs/epics/` that sequences versions, milestones, and units of work -- with their dependencies -- before implementation. A unit of work graduates into a working spec (`#ai-plan`) when it is picked up, and its epic entry becomes a pointer to that working spec.

**Why.** The working-spec tier (`#ai-plan`) maps one unit of work to one squash-merge, and the branch workflow caps a branch at one logical unit. A multi-deliverable initiative -- one needing a roadmap, version/milestone sequencing, and cross-unit dependencies settled before any code -- had no home: it was either forced into an oversized working spec (frozen on `Approved` before the plan has stabilized) or left undocumented. An epic is deliberately present-truth *by mutability* (the plan is revised in place as understanding changes) yet provisional and deleted on completion, so it never competes with the working spec or the reference spec as a source of shipped truth.

**Consequences.** The documentation model gains a record that is mutable-but-provisional, carried as a footnoted present-truth exception ([`documentation-model.md`](../reference-spec/documentation-model.md), [`records-architecture.md`](./records-architecture.md)). Provisional decisions and open questions live in the epic until they graduate to their standing register (`#swe-design-decisions`, `#swe-technical-debts`, `#swe-future-work`), so the epic is not a holding pen for findings actionable without it. The tier is optional and user-driven -- not wired into `#swe-done` or `#ai-plan` gates -- so a project with no multi-deliverable work never pays for it. The name overlaps the review board's `Epic` entity (`#ai-review-board`, [`entity-model.md`](../reference-spec/entity-model.md)); the two are disambiguated in place, not merged.
